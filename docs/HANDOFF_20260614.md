## Bug 全量记录（4 个）

### Bug #1 — `_ensure_connected()` 死锁

**表现**：`connect()` 启动后立即抛 `NotConnectedError`，无法完成 MCP 握手。

**根因**：鸡生蛋蛋生鸡的循环依赖。

```
connect()                           ← 目标：完成 MCP 握手
  → _request("initialize", ...)     ← 需要发 HTTP 请求来完成握手
      → _ensure_connected()         ← 检查 self._connected
          → self._connected is False ← 握手还没完成！
          → raise RuntimeError       ← 死锁
```

根本矛盾："发 `initialize` 请求"这个操作本身既是"建立连接"的手段，又是"被 `_connected` 守卫拦下"的对象。

**修复前流程**：
```
connect()
  → _request("initialize", ...)
    → _ensure_connected()        ← 检查 _connected → False → 抛异常
```

**修复后流程**：
```
connect()
  → _rpc("initialize", ...)      ← _rpc 只检查 self._http is not None（HTTP 层），不检查 _connected
    → HTTP POST /mcp
    → 返回 (response, headers)
  → 从 headers 提取 Mcp-Session-Id
  → 保存 negotiated_version
  → _rpc("notifications/initialized", ...)
  → self._connected = True       ← 握手完成后才标记
```

**修复代码**：`_request()` 重命名为 `_rpc()`，移除 `_ensure_connected()` 调用，仅检查 `self._http is not None`。`_ensure_connected()` 仅在对外 API（`list_tools()`、`call_tools()`、`preload_all_toolsets()`）中调用。

**文件**：[harness/client.py:250-261](harness/client.py#L250-L261)

### Bug #2 — Mcp-Session-Id 丢失

**表现**：MCP 握手成功（HTTP 200），但 `self._session_id` 为空字符串，后续所有请求缺少 `Mcp-Session-Id` header → UE 返回 `Missing session id` 错误。

**根因**：MCP 规范中 `initialize` 的 session ID 在 **HTTP response header** 中，不在 JSON body 中。

UE MCP Server 代码（[ModelContextProtocolServer.cpp:654](<UE_ENGINE_ROOT>/Plugins/Experimental/ModelContextProtocol/Source/ModelContextProtocol/Private/ModelContextProtocolServer.cpp#L654)）：
```cpp
UE::ModelContextProtocol::Private::CompleteWithResult(
    OnComplete, RequestId, InitializeResult, &Session->ID);
//                                           ^^^^^^^^^^^^
//                   Session ID 通过 HTTP response header 返回，不在 JSON body
```

`CreateJsonRpcResultResponse`（line 170-174）：
```cpp
if (SessionId) {
    ServerResponse->Headers.Add(McpSessionIdHeader, {*SessionId});
    //                          "Mcp-Session-Id"    f327ee3f...
}
```

**修复前流程**：
```
_rpc("initialize", ...)
  → HTTP response body: {"jsonrpc": "2.0", "result": {"protocolVersion": "2025-11-25", ...}}
  → 仅解析 body，忽略 headers
  → self._session_id = ""（丢失）
```

**修复后流程**：
```
_rpc("initialize", ...)
  → 返回 tuple[JsonRpcResponse, dict[str, str]]
  → resp_headers = {k.lower(): v for k, v in response.headers.items()}
  → connect() 提取: self._session_id = resp_headers.get("mcp-session-id", "")
  → self._negotiated_version = resp.result.get("protocolVersion", ...)
```

**修复代码**：[harness/client.py:250-353](harness/client.py#L250-L353) — `_rpc` 返回值从 `JsonRpcResponse` 改为 `tuple[JsonRpcResponse, dict[str, str]]`。`connect()` 从 headers 中提取 `mcp-session-id`（小写，HTTP 标准要求）。

### Bug #3 — 0 个工具集（list_toolsets 解析失败）

**表现**：
```
发现 0 个工具集，开始预加载...
已预加载 0/0 个工具集
最终工具列表: 3 个工具
```

尽管 UE 端实际注册了 19 个工具集。

**根因**：MCP `tools/call` 返回格式是 content array，但解析代码只检查 flat 格式。

UE 返回的实际格式（通过 curl 验证）：
```json
{
  "jsonrpc": "2.0",
  "id": 10,
  "result": {
    "content": [{
      "type": "text",
      "text": "- ToolsetRegistry.EditorAppToolset: ...\n- SceneTools: ...\n- ActorTools: ..."
    }]
  }
}
```

修复前解析代码只检查了 key `"text"` 和 `"structuredContent"`：
```python
if isinstance(resp.result, dict):
    for key in ("text", "structuredContent"):  # ← 这两个 key 不存在
        if key in resp.result:
            catalog_text = str(resp.result[key])
            break
    if not catalog_text:
        catalog_text = str(resp.result)  # ← fallback: Python dict repr
```

`str({"content": [...]})` 产出 `"{'content': [{'type': 'text', 'text': '- EditorAppToolset: ...'}]}"` —— 一行，无换行，无 `"- "` 前缀行。解析出 0 个工具集名。

**修复后流程**：
```python
if isinstance(resp.result, dict):
    # 优先提取 MCP content array
    content = resp.result.get("content", [])
    for item in content:
        if isinstance(item, dict) and item.get("type") == "text":
            catalog_text = item.get("text", "")
            break
    # 兜底: flat 格式
    if not catalog_text:
        for key in ("text", "structuredContent"):
            if key in resp.result:
                catalog_text = str(resp.result[key])
                break
```

**修复前 vs 修复后**：
| | 修复前 | 修复后 |
|---|---|---|
| 发现工具集数 | 0 | 19 |
| 最终工具数 | 3（仅发现工具） | 211 |
| 耗时 | 瞬间（0 个加载） | ~5 分钟（串行，见 Bug #4） |

**修复代码**：[harness/client.py:405-421](harness/client.py#L405-L421)

### Bug #4 — load_toolset 超时（_rpc 缺少 SSE timeout）

**表现**：修复 Bug #3 后，`load_toolset` 串行调用全部成功但极慢——单次 ~16 秒，19 个工具集总计 ~5 分钟。

**直接原因**：串行循环 19 次 `load_toolset`。

**次要原因**：`_rpc()` 对 `tools/call` 未传 `sse_read_timeout`。

对比 `call_tool()` 和 `_rpc()`：
```python
# call_tool() — 正确传了 timeout
response = await self._http.post(
    ...,
    timeout=httpx.Timeout(self._config.sse_read_timeout),  # 60s
)

# _rpc() — 没有传 timeout，使用 connect() 时设置的默认 request_timeout (30s)
response = await self._http.post(
    self._config.ue_url_path,
    json=payload,
    headers=self._build_headers(),
    # ← 缺少 timeout！
)
```

`tools/call` 返回 SSE event-stream（两阶段：空流头 → 结果帧），需要比普通 JSON-RPC 更长的读取超时。

**修复**：
1. `_rpc()` 对 `method == "tools/call"` 使用 `sse_read_timeout`（60s），其他方法使用 `request_timeout`（30s）：[harness/client.py:272-282](harness/client.py#L272-L282)
2. `preload_all_toolsets()` 的串行循环改为 `asyncio.gather()` 并行加载：19 个 `load_toolset` 并发 → 总耗时 = 最慢那个

**修复代码**：
- SSE timeout：[harness/client.py:272-282](harness/client.py#L272-L282)
- 并行加载：[harness/client.py:437-450](harness/client.py#L437-L450)（用户已手动修改）

## 核心代码架构（当前状态）

### `harness/client.py` — `McpClientSession` 类

```
McpClientSession
├── connect()                  # MCP 握手: initialize → 提取 session_id → notifications/initialized
│   └── _rpc(method, params)   # 低层 JSON-RPC 2.0，不检查 _connected，仅检查 _http
│                                # 返回 tuple[JsonRpcResponse, headers_dict]
├── close()                    # DELETE /mcp 拆除会话
├── list_tools()               # → tools/list → 返回 list[dict]
├── call_tool(name, args)      # → tools/call → SSE 两阶段解析 → 返回 str
├── preload_all_toolsets()     # → list_toolsets → 解析工具集名 → 并行 load_toolset → list_tools
├── _ensure_connected()        # 仅对外 API 调用，检查 self._connected
├── _rpc(method, params)       # 内部 RPC: 构建 payload → POST → 解析 SSE/JSON 响应
├── _extract_tool_result()     # 从 SSE 事件流中提取最终工具结果
├── _build_headers()           # 构建 Mcp-Session-Id + Mcp-Protocol-Version headers
└── parse_sse_stream(bytes)    # 独立函数，解析 SSE 字节流 → list[SseEvent]
```

**关键设计原则**：
- `_rpc()` 是唯一发送 HTTP 请求的方法，不检查 `_connected`（被 `connect()` 自身调用）
- `_rpc()` 对 `tools/call` 方法使用 `sse_read_timeout`（60s），其他方法用 `request_timeout`（30s）
- `_rpc()` 返回 `tuple[JsonRpcResponse, dict[str, str]]` — callers 可以读取 response headers
- `call_tool()` 使用独立的 `_extract_tool_result()` 而非 `_rpc()` — 它有独立的 SSE timeout 和错误处理
- `preload_all_toolsets()` 使用 `_rpc("tools/call", ...)` 直接调用工具（不走 `call_tool()`）

### `harness/server.py` — MCP Server

- 使用 `mcp` Python SDK 构建 MCP Server
- `list_tools` handler：透传 UE 工具列表（P2 时加入 Context Assembler 过滤）
- `call_tool` handler：转发给 `ue_client.call_tool()`，返回结果

### `harness/config.py` — 配置

- `Config` dataclass：`ue_host/ue_port`、`listen_host/listen_port`、`ue_url_path`、`mcp_protocol_version`、`request_timeout`（30s）、`sse_read_timeout`（60s）、`preload_all_toolsets`（default True）
- `Config.from_env()` 从环境变量加载
- `Config.merge_cli_overrides()` 从 CLI 参数覆盖

## 关键技术细节（后续开发必读）

1. **UE MCP Server 的 SSE 响应格式**：所有 `tools/call` 返回 `Content-Type: text/event-stream`，格式为 `event: message\r\ndata: {json}\r\n\r\n`。`_rpc()` 和 `_extract_tool_result()` 都需要处理。

2. **MCP 协议版本 header**：`initialize` 后所有请求必须携带 `Mcp-Protocol-Version: 2025-11-25`（与实际协商版本一致）。

3. **MCP content array**：工具结果格式为 `{"content": [{"type": "text", "text": "..."}]}` 或 `{"content": [{"type": "image", "data": "base64...", "mimeType": "image/png"}]}`。不要假设 flat 格式。

4. **`_rpc()` vs `call_tool()`**：`_rpc` 是底层 JSON-RPC，可用 `method="tools/call"` 直接调工具（`preload_all_toolsets` 这样用）。`call_tool` 是高层封装，返回字符串结果。两者对 `tools/call` 都使用 SSE 解析，但 `call_tool` 的 timeout 和错误处理更独立。

5. **httpx 日志**：`INFO` 级别每个 HTTP 响应自动打一行 `"HTTP/1.1 XXX XXX"`。这些是 httpx 内部日志，无需手动添加。

6. **并行 HTTP 请求**：`McpClientSession._http` 是 `httpx.AsyncClient`，连接池默认支持并发请求。每个 `_rpc` 调用是独立的 HTTP 请求，UE 在 game thread 上串行处理。

7. **Windows 信号处理**：`loop.add_signal_handler` 在 Windows 上不可用（`NotImplementedError`），当前代码已有 fallback。
